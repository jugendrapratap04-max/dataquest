# UI and learning-experience audit — 2026-08-06

An external spec (generated from screenshots) proposed a large redesign. This
document is the audit that had to come first, plus a verdict on every part of
that spec, plus the plan.

**The instruction it was reviewed under: analyse it, do not follow it.** Some of
it is right and measurable. Some of it contradicts decisions this project made
deliberately and wrote down. Some of it is already built.

---

## 1. What was measured

Not opinions. Commands, on this repo and the live site.

| Thing | Measured | What it means |
|---|---|---|
| `app/globals.css` | **2,736 lines, 1,660 rules, 40 custom properties** | Almost every value is a literal typed into a rule. This is the single strongest argument in the whole spec. |
| Components | 41 top-level + 91 viz = **132** | Large but not chaotic. |
| `loading.tsx` files | **0** | There is no loading state anywhere in the app. |
| `error.tsx` / `not-found.tsx` | 1 / 1 | Root only. |
| ESLint | **2 warnings, 0 errors** | The codebase is clean. The old 33-error note is stale. |
| `:focus-visible` rules | **3** of 1,660 — **but one is global** | ⚠️ **Corrected after a closer look.** Line 116 is a bare `:focus-visible` applying to every element, so keyboard focus IS visible platform-wide. The real defect is narrower and worse: **six form controls set `outline:none` and put nothing back** — the topbar search, the todo input, the note form, one settings input, and both code editors (`.lc-area`, `.hw-area`). Focus lands on them and disappears. The first version of this table said keyboard users get "nothing"; that was wrong and is the kind of claim an audit exists to avoid. |
| `aria-*` attributes | 24 `aria-label`, 9 `aria-hidden`, 5 `aria-pressed` | Better than the spec assumes. |
| Lesson content start | **y=825** against a 720 fold (before the cap shipped) | Measured on a live lesson, not guessed. |
| Empty chapters | 8 found, 8 fixed | `/book` listed chapters that opened onto nothing. |

## 2. Verdict on the spec

### 2a. ACCEPT — right, and backed by the measurements

| Spec item | Why it stands |
|---|---|
| **Design tokens** (GLOBAL-001, DS v2) | 1,660 rules and 40 variables. Every colour tweak is a find-and-replace today. This is the foundation everything else needs. |
| **Loading / empty / error states** | Zero `loading.tsx`. Already on the `AGENTS.md` backlog and now evidenced. |
| **Focus states, keyboard navigation** | Not for the reason the spec gives — the global ring exists. But six controls delete it, including both code editors, and that is worth fixing. Already on the backlog as "keyboard walk". |
| **Visual hierarchy — one primary action per screen** (DS-001, DB-001) | Confirmed by walking the site: the dashboard's cards all carry the same border, radius and weight. |
| **Mobile is compressed desktop in places** (MB-001) | Confirmed at 390px on several screens. |
| **Reading: shorter paragraphs, calm lesson area** (LS-001, motion spec) | Agrees with the fold measurement and with this course's own writing rules. |
| **Motion: subtle, `prefers-reduced-motion`, no decoration** | The motion spec is the most disciplined part of the whole document. Its anti-pattern list is correct. |

### 2b. REJECT — wrong for this project, with the reason

| Spec item | Why not |
|---|---|
| **AI Mentor / AI Debugger / AI Code Review / AI interview** | Every one is a paid API call per student per message, forever, on a platform that costs ~₹0 to run. **Jugendra's own decision, on the record: "cost wale kaam ko rokte hai."** This is not a design question; it is the only line item with a bill. |
| **The proposed colour palette** (`#14100F`, `#FF9A4D`, …) | The spec's own golden rule says "do not redesign branding", then replaces the brand colours. Etudo has an amber/teal identity and **four working themes** driven by `--sub-h`. Adopting a new palette means rebuilding all four. |
| **Framer Motion as a dependency** | The spec later says not to install it without evaluating first. Everything it asks for at Levels 1–2 (opacity, 2px translate, progress fill) is CSS. A motion library is justified only when orchestration or presence is genuinely needed. |
| **"Friends studying now", social feeds, pair programming, live coding rooms, contests** | Real numbers: **16 users, 3 with a passing submission.** Social features here would show everyone an empty room — the same dishonesty as the seeded XP and fake leaderboard that were already removed. |
| **Confidence meter, AI mistake notebook, code-quality score, practice replay** | All need either AI or telemetry that does not exist. Inventing a "confidence" number would be a made-up metric on a platform that just deleted its made-up metrics. |
| **World Map, Boss Battles, Skill Galaxy, Mastery Rings** | Months of work each, aimed at engagement rather than learning. The stated identity is "calm, premium, long-term mastery over short-term engagement" — these are the opposite. |
| **Confetti / celebration everywhere** | The spec contradicts itself here and its motion section is right: celebration is for rare milestones. Confetti already exists (`Celebrate.tsx`) and fires on solve. |

### 2c. ALREADY BUILT — do not redo

Reading progress bar · sticky table of contents · code blocks with Run and Reset
(`LiveCode`) and live preview (`LiveHtml`) · XP, levels, badges, streak, year
heatmap, achievements (`/profile`) · "Continue where you left off"
(`/dashboard`) · error explanations mapped to lesson mistakes (`ErrorHelp`) ·
four themes with a scheduler · focus mode · subject picker (`/learn`) ·
practice linked from the end of every lesson, guests included.

**Roughly a third of the spec's "add this" list is already shipped.** Anyone
implementing it top-to-bottom would rebuild working features.

### 2d. DEFER — right idea, wrong moment

Spaced-repetition revision engine · skill tree / knowledge graph · offline
support · gesture navigation · community solutions. All defensible; none is the
current bottleneck.

## 3. What the bottleneck actually is

The spec assumes the problem is polish. The measurements say otherwise:

1. **No loading states.** Every page is blank and then complete. On a slow
   Indian connection that reads as broken, and it is the first impression.
2. **No token layer.** 1,660 rules means every visual change is a sweep, so
   improvements get expensive and stop happening.
3. **Six controls hide their own focus ring** — including both code editors, the
   places a keyboard user spends the most time.
4. **Everything weighs the same.** Nothing tells a student where to look.
5. **The HTML course has no quizzes or drills** — `npm run syllabus` reads
   26/35 at the bar, **0/35 at FULL**. That is a learning-experience gap, and
   the spec never mentions it because a screenshot cannot show it.

Point 5 matters most for "improving the learning experience" and is invisible
to any visual audit.

## 4. On the five-document recommendation

The advice was five documents before any code:
`PROJECT_AUDIT`, `DESIGN_SYSTEM`, `COMPONENT_ARCHITECTURE`,
`IMPLEMENTATION_PLAN`, `TASKS`.

**Taken: the sequencing.** Audit → plan → page by page → test. That is right,
and shipping all of this at once would produce exactly the inconsistency the
spec warns about.

**Not taken: five files.** This is one person's project. `COMPONENT_ARCHITECTURE`
and `IMPLEMENTATION_PLAN` and `TASKS` would repeat each other and go stale in a
week — `AGENTS.md` already carries the working rules and is read every session.
So: **this document** (audit + verdict + plan) and **`DESIGN-SYSTEM.md`**
(tokens + component contract). Two files that will be maintained beat five that
will not.

## 5. The plan

Each phase ships on its own and is verified before the next starts. No phase
depends on a redesign.

### Phase 1 — the floor (highest value, lowest risk)
- [ ] **Design tokens.** Lift colour, spacing, radius, shadow and motion values
      out of the 1,660 rules into one token block. No visual change — the same
      values, named. Everything after this becomes cheap.
- [ ] **Focus states.** The global ring already exists; give the six controls
      that delete it a visible replacement.
- [ ] **Loading states.** `loading.tsx` for dashboard, lesson, practice,
      roadmap, book. Skeletons that match the final layout.
- [ ] **Empty and error states** for every page that fetches.

### Phase 2 — hierarchy
- [ ] One primary action per screen; secondary cards lose border weight.
- [ ] Dashboard: hero dominates, everything else recedes.
- [ ] Lesson: the reading column is the calmest thing on the page.

### Phase 3 — mobile as its own layout
- [ ] Bottom navigation, thumb-zone actions, 44px targets.
- [ ] Sticky "next" on lessons; run button always visible in practice.

### Phase 4 — motion, at Levels 1–2 only
- [ ] Hover/press feedback, progress fill, count-up on change only.
- [ ] `prefers-reduced-motion` honoured globally.
- [ ] Celebration reserved for lesson complete, module complete, level up.

### Phase 5 — the learning gap
- [ ] Quizzes and drills for the HTML course (0/35 at FULL today).
- [ ] Revision engine, if the numbers justify it.

---

## 6. Rules for whoever implements this

- Do not adopt the spec's palette. Tokenise the palette that exists.
- Do not install a motion library before proving CSS cannot do it.
- Do not build anything that needs an AI call without saying what it costs.
- Do not add a social feature until there are enough users for it to be true.
- Ship one phase, verify it on the live site, then start the next.
- Every number in a UI must come from the database, not from prose.
